# Architecture & module contracts

A first-person cab ride along a street tram line through a limestone city street.
Browser app, three.js r186 (vendored, `vendor/three`), plain ES modules with no build step.

Run: `python3 serve.py` (or any static server at the repo root) and open `http://localhost:8080/`.

## Hard rules (apply to every file)
- **Blind comparison**: nothing in the project may say how the work was produced. No tool or vendor names in metadata (glTF `generator`/`copyright` fields, image EXIF/XMP, page titles), and no "generated by" wording in code, comments, file names, titles or commit messages.
- Only `reference/*.jpg` describes the scene. Do not search the web for this street/city or for existing models of it. Never use the reference photos as textures.
- All geometry and textures are procedural (JS at runtime, or Blender/Python scripts in `tools/`), or freely licensed assets recorded in `docs/ASSETS.md` with their licence.
- Photoreal is the goal: real-world scale, PBR values, no toon/flat/low-poly look, no primitive placeholders in the final result.
- Content is deterministic: identical on every visit (see `src/core/rng.js`).
- Keep all work inside this repository. Scratch output goes to `.work/` (git-ignored).

## Tooling
- `tools/shoot.py`: headless Chrome on the GPU. It starts a private static server, opens the app, waits for `window.__ready`, saves screenshots and prints console errors and `stats` (fps, frameMs, gpuMs, draw calls, triangles, per-module chunk build ms).
  - `python3 tools/shoot.py --params "s=420&tod=0.55" --out .work/shots/x.png`
  - `--shots 4 --interval 0.5` makes a sequence. `--eval "<js>"` evaluates and prints (it may be an async IIFE). `--settle 3` waits longer. `--pre "<js>"` runs right after ready. `--init "<js>"` runs in the page before its own scripts (to hook or stub a browser API for a test, e.g. hold back `requestAnimationFrame`).
  - It waits up to `--timeout` (240 s) for ready, printing progress every 30 s (a page whose main thread does not answer for 120 s is reported and waited for). When the app never becomes ready it prints a WARNING, takes no screenshots and exits 1 (`--force` shoots the partly loaded page anyway). When the browser held back the animation frames during the start-up it prints `first frames held back by the browser:` with `perf.init.firstFrameStall` (see Start-up).
  - **Frame rate**: Chrome runs with vsync off, so an uncapped loop queues frames ahead of the GPU and then blocks inside GL calls. That inflates CPU times (p95 36.6 ms uncapped against 9.8 ms capped on the same ride) and logs storms of 50-110 ms `gpu-wait` frames that a display-synced browser never has. `--fps N` caps the app's `requestAnimationFrame` at N from ready on, as vsync would; timing runs (`--hitches`, `--heapprof`, `--heaplive`) default to `--fps 60`, everything else runs uncapped (`--fps 0` uncaps a timing run). Budget rides use `--fps 30`. GPU time is the same capped or uncapped.
  - Ride timing: `python3 tools/shoot.py --params "s=1700&speed=45" --shots 0 --settle 30 --hitches` resets the frame statistics at ready and prints the hitch log at the end (see Frame timing). Timing runs also sample every frame after ready and print `frame samples`: percentiles (n, p50, p95, max) of the frame interval, the frame-callback CPU time, the frame's GPU time (`gpuTimer.of(frame)`), draw calls and triangles, and the frames over 28 ms GPU or 20 ms CPU. Screenshots stall frames, so time rides with `--shots 0`.
  - `--heapprof 30` samples JS allocations (garbage included) from ready to the end and prints the top 30 allocation sites with MB and MB/s. Compare runs per frame (site MB / `frames`), not per second. `--heaplive N` samples the allocations since ready still alive at the end (what the heap grows by; typed-array data not included), `--snapshot PATH` saves a heap snapshot after collecting garbage, `--cpuprof N` profiles the start-up main thread by file and function with the calling module. `--profile <dir>` keeps a Chrome profile (and its GPU shader cache) between runs.
  - Timing runs print the machine's load at the start and the end: load average per core, headless browsers running, GPU utilisation. Other processes often render on the same machine, so CPU cores and the GPU are shared: judge frame times on the `usual` values and the `contention` / `gpu-wait` causes in the hitch log, repeat a run before blaming a module, and run budget checks serially on a quiet machine. Structural counts (allocations per frame, draw calls, triangles, upload bytes, program re-evaluations) are reliable under load; milliseconds are not.
  - `--heapdelay S` (with `--hitches`, `--heapprof` or `--heaplive`) starts sampling S seconds after ready and resets the frame statistics then: a short run is otherwise dominated by warm-up allocation while V8 has not yet optimised the code (the crowd measured 106 KB/frame over 25 s against 52 KB/frame over 70 s of the same code).
  - `--firstdraw` hooks WebGL from page start and lists, at the end, every program whose first non-empty draw came after ready (with the frame, route position and the materials using it; shadow `customDepthMaterial`s included) and the programs never drawn. Each late first draw costs the GPU process 100–200 ms mid-ride (see Start-up). Run it, and any timing QA, with a warm `--profile <dir>`: a fresh profile has no shader cache, so its long compiles hide first-draw stalls.
  - **Browser lifetime**: an orphaned headless Chrome renders uncapped and holds the GPU (once for 78 minutes at 97 %). Chrome and the private server run in process groups of their own, and both tools kill the whole group however they end: normally, on an exception, on SIGTERM, SIGINT or SIGHUP (as `timeout` sends; the tool exits 143, 130 or 129, and `timeout` itself reports 124), at interpreter exit, and through a watchdog process holding a pipe to the tool when the tool itself is killed with SIGKILL. The server also exits by itself once its tool is gone (`serve.py <port> <bind> --owner=<pid>`). `--max-seconds S` bounds a run (default `--timeout` + `--settle` + the shots + 900 s; 0: no limit; exit 124 when it passes). Each run first reaps what earlier runs left behind: browsers tagged `--shoot-owner=<pid>` whose tool is gone, untagged headless browsers with a profile under `.work/` whose parent is no longer a Python script, orphaned tool servers and scratch profiles (`.work/shoot-*`, `.work/record-*`) older than 15 minutes that no process uses. `--reap` does only that. Still run every capture under `timeout`.
  - Chrome picks its own DevTools port (`--remote-debugging-port=0`, read back from `<profile>/DevToolsActivePort`), so runs started at the same moment never meet on one port. Environment: `SHOOT_GPU_FLAGS` replaces the GPU switches, `SHOOT_CHROME_FLAGS` adds switches (for example `--js-flags=--trace-deopt`), `SHOOT_STDERR=<file>` keeps Chrome's own output.
- `tools/record.py`: offline movies. The page runs with `rec=<fps>`, every frame advances the clock by exactly 1/fps, frames are grabbed through the DevTools protocol and encoded with ffmpeg in the tools image: `tools/record.py --name midday --params "s=700&tod=0.1" --seconds 40` writes `.work/movies/<name>/` (frames in `frames/*.jpg`, `<name>_1080p.mp4`, `<name>_phone.mp4`). Browser lifetime as shoot.py; `--max-seconds` bounds the browser part (default `--timeout` + 2 s per frame + 900 s), and encoding runs after the browser is closed.
- `tools/dk <cmd>`: runs a command in the Docker tools image (`docker/Dockerfile`: Blender 4.5 LTS, Node 24, Python + numpy/scipy/Pillow, ImageMagick, ffmpeg, gltf-transform), with the repo mounted at `/work`.
  - Blender: `tools/dk blender -b --factory-startup -P tools/blender/<script>.py -- <args>`. Write outputs to `assets/<area>/`.
  - `DK_GPU=1 tools/dk ...` adds the NVIDIA GPU (Cycles baking). `tools/dk node <file.mjs>` runs plain-JS checks (no `three` import map there).
- URL parameters (core ones in `src/core/params.js`): `s`, `tod`, `fov`, `speed` (starting speed; the auto driver then picks its own cruise), `auto`, `freeze=1`, `rec=<fps>` (offline recording: fixed time steps, frames stepped by `app.recStep(n)`, see `tools/record.py`), `capture=1`, `only=a,b`, `skip=a,b`, `view=s,d,h,yawDeg,pitchDeg` (free inspection camera in route coordinates; yaw + turns left), `q=low|med|high`, `debug=1`, `seed`.
  - Isolate your module while iterating, e.g. `only=street` (core modules materials/env/train/cameraRig always load). Add `post` to `only` to include post-processing and `farfield` to include the far field; `skip=farfield` drops it.
  - Inspection and A/B switches: `sky=streaks|cumulus|haze` (cloud and aerosol regime), `tram=<s>` (first oncoming tram's nose), `prof=1` (post's per-section GPU timers in `app.post.timings`), `taa=0`, `taaj=<px>`, `sharp=<k>`, `lhr=0` (post's local highlight recovery off), `debug=1` (also `stats().badPixels`), `ffnear=<m>` (start the far field nearer, to compare it with the real chunks), `fftrees=0` (the far field's procedural crowns instead of the vegetation's far trees), `catglow=0` (catenary's lantern aureoles off; post's glow pass stands in), `cabshadow=0|2` (trams: the cab tram's shadow off, or kept under `view=` to see it from outside), `facglass=r|t|m|e` (facades: one term of the shop glass), `audio=1`, `audiocache=0`.
  - Core A/B switches: `boot=serial` (every module inits before the start-up prime and compile, as before the overlapped start-up), `lightloop=0` (three's unrolled spot-light loop), `glbox=0`, `glsort=0`, `gltyped=0` (core's allocation-free scalar uploads, render-list sort and typed uniform setters, see Frame timing).
  - Light and sky inspection: `mie`, `mieh`, `miealb`, `mieg`, `mieang` (aerosol Angstrom exponent, default 0.6), `alt`, `hlev`, `shadowmap=<texels>` (sun atlas tile size) (env), `hslope`, `skychroma`, `skysat` (post). Module-private debug switches (`crowd_*`, `crowdCheck=1`, `veg*`, `cat*`, …) and harnesses (`humanstest=1` with `ht_*`, `propstest=1`) are described in each module's header. humans: `humans_src=<dir>` (another build of the cast), `humans_tex=2` (texture arrays at half resolution), `humans_lod=a,b,c` (LOD thresholds), `humans_prof=1` (GPU timers of the figures and their shadows), `humans_dbg=1..8` (occlusion, albedo, beard edge, skin decals, regions, no skin, hat brim, hair fade), `humans_bind=1` (bind pose), `humans_brows=0` (the brow cards instead of brows on the skin), `humans_face=<k>` (scale of the per-person face shapes).
  - Close-up inspection: `view=430,9,1.7,-60,8` stands on the right sidewalk at s=430 and looks right-ish towards the facades. Yaw −90 looks straight at the right-hand facades and +90 at the left-hand ones.

## Coordinates & conventions
- Metres, Y up, three.js right-handed. 1 UV unit = 1 metre on every library material, so geometry UVs must be in metres. Materials handle texture scale.
- **Route coordinates** `(s, d, h)`, see `src/world/route.js`. `s` is distance along the street centre line (wraps at `route.length`, about 6 km, a closed loop). `d` is the lateral offset, + to the right of travel. `h` is height above the paving. Rail tops are flush with the paving at h = 0.
  - `route.toWorld(s, d, h, out?)`, `route.sample(s, out)` → `{pos, tan, tanH, right, heading, curvature, grade}`, `route.heading(s)`, `route.curvature(s)` (+ = left curve), `route.elevation(s)`, `route.grade(s)`, `route.offsetScale(s, d)` (= 1 + κd, arc-length scale of an offset line), `route.wrap`, `route.delta(a, b)`, `route.project(x, z, sHint, range = 30, out = null)` → `{s, d}` (fills `out` when given), `route.segments`, `route.segmentAt(s)`. Pass `out` in per-frame code: without it toWorld allocates a vector. `sample(s, out)` makes no garbage once `out` holds its vectors; toWorld and surface box no numbers inside.
  - Allocation-free entry points for per-agent and per-vertex loops: `route.toWorldOf(o, out)` is `toWorld(o.s, o.d, o.h ?? 0, out)` read from o's fields. `route.io` is a `Float64Array(8)`: inputs `[0] s, [1] d, [2] h`; `route.toWorldIO(out)` reads them, and `route.sampleIO()` writes the outputs `[3] heading, [4] curvature, [5] elevation, [6] grade` (`[7]` is scratch). The crowd uses these (falling back to toWorld, heading and curvature where `route.io` is absent).
  - `object.rotation.y = route.yawAt(s)` makes local −Z point along travel (+X to the right). `rotation.y = route.heading(s)` makes local +X point along travel.
  - Elevation: gentle periodic rolling, periodic hills (`route.hills`) and mesas (`route.mesas`: an eased climb at a steady grade, a level top, an eased descent). The default start (s = 25) stands in a shallow sag at the foot of the main avenue, which climbs 21 m at about 5.8 % from s ≈ 240 to 510, levels off at about 600 (the first stop) and descends from 740 to 1300. The steepest grade on the loop is 5.9 %.
- Street cross-section (`src/core/config.js`): standard gauge 1.435 m. Rail centre lines are at `±RAIL_CENTER` (0.7455) from each track centre. Track centres are at `d = ±TRACK_OFFSET` (1.6). The camera rides the **right** track (d = +1.6). The paved track corridor spans `|d| ≤ TRACK_ZONE_HALF` (3.4), with a light stone edge band `EDGE_BAND_W` on each edge. Pole line `POLE_D` = 3.95, tree line `TREE_D` ≈ 5.15. Facades sit at `|d| = layout.halfWidth(s, side)` (≈ 11–13.5 m). Driver eye: `EYE_HEIGHT` 2.75 m. Contact wire: 6.0 m.
- **Ground**: `route.surface(s, d)` shapes the ground outside the track corridor: sidewalk cross-fall, a hillside tilt and settlement undulation, level beyond about the facade line. `route.toWorld(s, d, h)` and `route.groundY(s, d)` include it, so always place objects with toWorld (h = height above the local paving). Never use `route.sample().pos` plus your own offsets for ground contact. The street mesh adds its own millimetre detail (gutters, crowns) on top: `app.systems.street.heightAt(s, d)` is the paving as drawn.
  - Within 0.9 m of a facade the paving meets the building's own ground line (lot frame chord, `plan.groundAt(u)`). Objects standing against facades use `plan.groundAt` or `street.heightAt(s, d)`, not toWorld with h = 0. Corner returns and cut faces have a varying `groundAt(u)` (`frame.ground0 ≠ frame.ground1`), eased into the side street.
  - Side streets: `street.mouth(c, side)` → `{start, along, dirOut, len, hw, half, road, sw, kerbH, rampX, level}`, the mouth frame of cross street `c` (a point at mouth coordinates (a, x) lies at `start + along·a + dirOut·x`: a across the side street, x out from the main facade line), and `street.sideHeightAt(c, side, a, x)` its paving height (carriageway a kerb below the sidewalks, ramped up from the mouth). Things up a side street are placed and drawn in this frame.
- **Facade frame** (per building lot): `lot.frame = {origin, uDir, nDir, up, width, ground0, ground1, floorRef, matrix}`. `u` runs along the facade and increases to the viewer's right when looking at the facade from the street. `v` is up from `floorRef`. `w` points out of the wall toward the street, so recesses are at w < 0. `frame.matrix` maps (u, v, w) to world. The frame is right-handed, so CCW winding seen from the street is front-facing. Ground (paving) height along the facade is `plan.groundAt(u)`, which is ≤ 0 because the street slopes.

## Layout (shared master plan): `src/world/layout.js`
Deterministic and computed once. **Read placements from here and never invent overlapping ones.**
- `stations[]`: `{id, s, len, stopS, platforms:[{side, s0, s1, d0, d1, h}]}`. Side platforms are 2.9 m deep and 0.30 m high, on both sides of the corridor. The cab tram stops with its front at `stopS` (32 m body behind); an oncoming unit stops at the mirrored `2·s − stopS` (as trams.js plans it). The street's oil and drip wear under the standing trams follows these values and the bogie positions of `AXLES` (`src/core/config.js`), so changes to either must be announced.
- `crossovers[]`: `{s0, s1, len, from}`, a single crossover between the tracks. `from:+1` means facing points on the ride track at s0 diverging to the left track by s1.
- `crossStreets[]`: `{s, width, side (0 both | ±1), depth, angle, junction?}`. No lots, trees or poles in the mouth.
- `lots[]` (main street): `{id, side, s0, s1, len, d, seed, depth, cornerStart, cornerEnd, cornerU0, cornerU1, frame, cafe?}`. `sideLots[]` line the cross streets: `{..., sideStreet:true, cross, edge, x0, x1, frame}`. `lot.cafe` is the index of the lot's terrace in `cafes`.
- `poles[]`: `{s, side, d, lamp, banner}`, shared by lamps and catenary (catenary draws a banner on about a third of the flagged poles).
- `trees[]`: `{s, side, d, seed, height, crown, mature}`: young trees 5.0–7.2 m tall with 2.6–3.8 m crowns, about 18 % mature (8–11 m, 4.5–6.5 m). Vegetation picks the drawn species, age and size from these with its own draws (about one old tree in ten on the avenue, s < 1500, and one in five elsewhere) and writes the drawn values back in its init: `height` (top of the drawn leaves), `crown` (drawn leaf spread, mean width over the two axes), `mature`, `crownR` (farthest leaf reach from the stem; crowns are off-centre, so use it for clearances), `crownBase` (lowest leaves above the paving), `species`, `template`, `drawn: true` and `planned {height, crown, mature}` (the layout's own values). Modules reading trees in `build()` see the drawn values; modules whose init runs before vegetation's (street, buildings, facades, ironwork) see the planned ones in their init. A young street tree keeps a clear stem: its crown starts at 2.85 m at the lowest and its lowest hanging leaves at 2.45 m. `vegetation.crownAt(t)` gives `{r, base}` of a tree's drawn crown (café canopies use it).
- `cafes[]`: `{id, lot, side, s0, s1, dIn, dOut, style ('umbrella'|'open'|'awning'), chairStyle, tables:[{s, d, shape, chairs:[{s, d, yaw}], dressed, places}], umbrellas:[{s, d, size, color}]}`. Chair yaw is a route-relative heading offset, and the chair faces the table.
  - A terrace belongs to one shop: 5–14 m of sidewalk centred on a ground-floor shop of its lot (else its entrance), at most 10 tables (about 4 on average) in one loose row, sometimes two (a second row only where it leaves a walking band beside the tree line). About 250 terraces on the loop.
  - Terraces come in runs of 2–4 neighbouring lots of a block (1–3 elsewhere). About 28 % of the frontage is café on the main avenue (s < 1500; its right-hand side a little more), within 130 m of a stop and at cross-street corners, and about 10 % elsewhere (error diffusion per side keeps it steady). The right-hand sidewalk ahead of `defaultStartS` always opens with a run. About 70 % of terraces are `'umbrella'` style; two terraces without umbrellas never follow each other in a run.
  - `umbrellas[]`: square market umbrellas packed edge to edge (about 0.3 m apart) over the whole terrace, `size` 3.0–4.0 m, one `color` per café (cream, white, a few navy, the odd sand or burgundy). `d` keeps the canopy at least 0.36 m inside the facade line, and `dIn` always lies at least 0.5 m beyond the umbrella row.
  - Furniture writes `tables[].dressed` (0 bare, 1 laid, 2 in use) and `tables[].places` (chair indices with a place setting) at init, and relaxes chair and umbrella positions and writes them back. The crowd seats patrons at the set places of dressed-2 tables first, then occasionally 1, never 0.
- `furniture[]`: `{type, s, d, yaw, ...}`. Types: bin, bench, bollard, planter, kiosk, advertColumn, bikeRack, infoBoard, shelter, ticketMachine, stopSign.
- `obstacles[]` (for the crowd): circles `{kind:'circle', s, d, r}` and rects `{kind:'rect', s0, s1, d0, d1}` (cafés, platforms, shelters carry their id). Query with `obstaclesNear(s, range)` or `inChunk('obstacles', i)`.
  - `layout.addObstacles([...])` registers obstacles for free-standing things a module places itself (A-frame boards, goods stands…): they join `obstacles` and the chunk buckets (obstacles pushed straight into `obstacles` reach the buckets at the next lookup too). Call it in `init`: the crowd reads the obstacles in its own init, which runs after every world module's.
  - Goods stands (facades, in its init): `{kind:'rect', s0, s1, d0, d1, stand: <kind>, lot: <lot id>}`, kind produce, citrus, flowers, clothes, news, bakery, sacks, bins, shoes or books. About 460 on the loop, each 0.25 to about 1.25 m out from the main-street facade line and never in a doorway, café terrace or cross-street mouth. Modules that place things on the pavement later (furniture's A-boards, through `obstaclesNear`) keep off them.
- Per-chunk lookup: `layout.inChunk(kind, chunkIndex)` for kind in lots, sideLots, poles, trees, cafes, furniture, obstacles, crossStreets, stations, crossovers. Helpers: `halfWidth(s, side)`, `chunkIndex(s)`, `isInStation(s, m)`, `isInCrossStreet(s, side, m)`, `isInCrossover(s, m)`, `nextStation(s)`, `defaultStartS`.

### Facade plans: `src/world/facadePlan.js`
`facadePlan(lot)` returns the architectural plan of a lot (cached, deterministic): floors, bays, openings, balconies, string courses, cornice, parapet, roof, rooftop clutter, signs, flags and style. It is shared by `buildings`, `facades`, `ironwork`, the crowd (doors) and the far field. Extending it is fine; renaming fields is not.
- Openings: `{id, floor, bay, uc, w, y, h, kind (shop/door/window/balconyDoor), top (flat/round/segment/pointed), rise, recess, shutters, lit, curtain, awning, ac, flowerBox, backDepth, group?}`. `o.backDepth` is the interior box depth behind the glazing. `shutters` is `'roller' | 'open' | 'closed' | 'none'` (null on older openings and on modern windows, where facades decide the roller shutters), `roller` the share of a roller shutter let down (0..1), `ac` a split unit under the window.
  - Arcaded triple windows: each light has `o.group = 3`, so several openings can share one bay and floor; the outer lights' ids end in `l` and `r`. Lights are 0.55–0.8 m wide, arched, with `shutters` null.
- Bays may differ in width (`plan.style.rhythm`: `'even'`, `'centre'` (a centre bay 1.4–1.75× wider) or `'ends'` (wider end bays)): use each bay's own `u0`/`u1`/`w`, never `bays[0].w`.
- `plan.style`: `{era, tint, tone, courseH, blockL, tooled, rusticGround, quoins, pilasters, surrounds, windowTop, shopTop, frameColor, shutterColor, finish, render, stone, rhythm}`.
  - `tint` is the absolute stone tint (cream `[0.86, 0.80, 0.68]` = the library texture as baked); buildings use `(tint / cream)^1.25` as the vertex tint. Weighting: honey and golden on about half the lots, pale and grey on about a fifth (`materials.meta['stone.ashlar'].tintWeights`). `tone` is the `STONE_TINTS` index of the base tint; neighbouring lots mostly differ in tone group.
  - `finish: 'render'` (else undefined: ashlar) marks a rendered, colour-washed front: about 60 % of the modern lots, about 7 % of the Mandate-era fronts (pale lime washes) and every landmark terminus (warm washes). `render = {color (multipliers on the plaster albedo), from (v where the render starts: top of the first string course, or the first floor)}`, and `stone` holds the stone tint of its dressing and stone-clad shop floor. For such lots `tint` holds the render's colour expressed as a stone tint, so anything coloured from the tint follows the wash; parts that are stone (shop recess linings, stone balcony slabs and corbels) should use `style.stone`. On a washed older front `style.frameColor` keeps its painted-timber colour.
  - Era mix: 24 % `'modern'`: wide flat windows 1.55–2.3 m wide, a thin coping for a cornice (h 0.25–0.4), a solid parapet, a flat roof and up to 9 floors.
- `plan.coursing {ch, v0}`: sills aligned per floor, heads snapped to courses.
- Head dressings: `headDressing(plan, orn, o)` → `{u0, u1, top, keyT?}`, the head dressing of opening o as the building shell draws it (arch rings and keystones, flat arches, lintels, hoods, crossettes, door portals): its extent along the wall, its highest point and, on arched heads, `keyT = [t0, t1]`, the keystone's span of the head parameter. Ground-floor heads stay under `plan.groundHeadLim` (the v under the first-floor soffits less 0.8 m of console room; null when no limit applies), so the shop arches stop well below the balconies; `plan.groundSegment` is true where the front's round shop arches were made segmental to keep under it. A balcony slab over a bay may be widened only part of the way, up to the bay's limits, giving its consoles room beside the head dressing below.
- `plan.cuts` and `plan.returns[]`: corner returns and chamfer faces with their own frames (`isCut`, `cut`). Facades must iterate `plan.returns` generically.
- `plan.vista` (number): how many cab positions, sampled every 20 m, have their deepest line of sight end within 25 m of the lot (main-street lots; 0 elsewhere).
- `plan.upper`: a set-back volume on a flat roof (penthouse or a later addition of several storeys), with its own facade frame (front at w = −setback): `{setback, u0, u1, width, depth, v0, floorH, floors, material, color, openings, frame, addition, balconies, sides, tower, mural, selfDressed: true}`. Buildings dresses it itself, so other modules may ignore it.
  - `balconies`: `[{u0, u1, y, depth, slabT, solid, floor}]` on additions.
  - `sides`: `[openings of the u = 0 side, openings of the u = width side]` or null. A side face's frame follows buildings' `sideFrame`: on the u = 0 side u runs from the back to the front, on the u = width side from the front to the back; the normal points outwards.
  - View-terminating lots: `terminusLots()` lists every one, towers and landmarks alike, and corner lots can be termini. A tower (`plan.upper.tower = true`) is a plain modern block of several more storeys, windows on every side, and on some a painted mural `mural = {e (side), k (0..5: buildings sink key 'mural<k>', material 'buildings:mural<k>'), u0, u1, v0, v1}` on the side facing back down the street. A landmark has a colour-washed front and no tower; corner termini are always landmarks.
- `plan.relief` (what the masonry puts on the wall face), `archSegments(o, q)`, `archPoint`, `openingOutline`, `ornament(plan, rng)` and `archRise` are exported helpers. Backdrop lots from `buildings.extraLots()` are dressed by facades (no `selfDressed`). Buildings owns door thresholds and steps. Facades dresses café 'awning' terraces with a continuous awning (hem about 2.7 m).
- Balcony consoles (ironwork): see World module contracts.

## Module system: `src/main.js`
Each module is a file whose default export is an object:
```js
export default {
  name: 'street',
```

- Modules are loaded with dynamic `import()`. A module that throws at load, init, build or update is logged and disabled, and the rest keeps running. **Never statically import another module's file.** Use `app.systems.<name>` (or the aliases `app.materials`, `app.env`, `app.post`, `app.train`, `app.cameraRig`, `app.crowd`, `app.humans`, `app.audio`, `app.ui`, `app.trams`). Static imports are fine for `src/core/*`, `src/world/{route,layout,facadePlan,streaming}.js` and `vendor/three`. A pure helper of another module (for example facades' `shopDecision(plan, o)` in `src/world/facades/shops.js`, the door, setback and roller-shutter decisions exactly as the facades draw them, or ironwork's `ironNeglect` in `src/world/ironwork/mats.js`) may be loaded with a guarded dynamic `import()` that falls back when it fails.
- `chunk = {index, s0, s1, lod, group, rng(tag)}`, with CHUNK_LEN = 40 m. Detail levels: `lod` 0 within `LOD0_DIST` (200 m), 1 out to `VIEW_AHEAD` (680 m) and 2, the far field, from there to `VIEW_FAR` (1400 m, `src/core/config.js`). A module is asked to build the levels in its `lods`; only the far field (`src/core/farfield.js`, core) builds lod 2. Chunks are rebuilt at a finer level as they come close.
- `build` must be fast: **target < 3 ms per chunk per module** (the streamer time-slices about 7 ms per frame across modules). Precompute shared geometry in `init`. Reuse geometries (`geometry.userData.shared = true` so they are not disposed). Merge per material with `MeshBatcher` (`src/core/geom.js`) or use InstancedMesh per chunk.
- `app`: `{THREE, renderer, scene, camera, canvas, params, U, events, route, layout, world, systems, time, dt, realDt, frame, startS, cameraS, perf}`. `app.dt` is 0 when frozen, and `app.realDt` is the wall-clock delta, clamped to [0, 0.1] s (exactly 1/fps under `rec=`), so neither goes backwards or jumps after a stall.
- `window.__app.stats()` returns perf counters.

### Start-up
Chrome compiles WebGL programs one after another in its GPU process (about 9 s for 130 programs), the longest part of the start-up, so the programs are queued as soon as they can be known and compile while the main thread goes on (KHR_parallel_shader_compile):
1. materials, env, post and the world modules (`src/world/*`) init in registry order. humans' init starts right after post's and runs alongside them (its init depends only on materials, env and post and mostly waits for the cast's download and decode); such an early init adds its scene content in one synchronous step;
2. their parts of the chunks within 240 m are built (`world.prime(s, 240, …, only)`);
3. the other modules (trams, humans, crowd, train, cameraRig, ui, audio, then the far field) init in registry order. As soon as the warm-ups still polling their programs are done (the texture bake, post's and env's passes: every `renderer.compileAsync` in flight, and `materials.ready`), the programs of everything in the scene are queued (`renderer.compile`, nothing waits) at the next module boundary, and the remaining inits run while the GPU process compiles;
4. their chunk parts (humans' parked bicycles) and the far field are built, their programs queued, and the start-up waits for every program (`compileAsync`), resolves their uniforms (`touchPrograms`), then runs frames until every chunk within 160 m is ready and sets `window.__ready`.

What this asks of modules:
- **No synchronous GL calls in init or in timers that run during the start-up**: a first draw of a program, `getUniforms`, `readPixels`, `getError`, a query of a program's status or a first `getExtension` each wait until the GPU process has worked through every program queued before it (seconds once the scene's programs are queued; the materials bake's own waits cost 0.5 s in step 1). Core enables the extensions three asks for on first use before anything is queued. Querying `isReady()` / `COMPLETION_STATUS_KHR` is a synchronous call too, so nothing polls programs between the queueing and step 4 (a module's own `compileAsync` warm-up in step 1 is waited for before the queueing).
- Inits in step 3 run after the world modules' chunks near the start are built: a world module's `build()` must not depend on the state of a step-3 module's init (none does; `app.train` and `app.trams` are read at update time), and no world module's init may use humans.
- `perf.init.firstFrame` separates the two parts of the time after the compile: the browser delivering the first animation frame and the first frames themselves (texture and geometry uploads, about 1 s). The browser now and then holds back the animation frames right after the start-up (before the first frame or after it) while the main thread stands idle: mostly for under a second, at times for seconds, more often with the GPU busy with other work, and on rare starts for over two minutes behind a frozen loading screen (124.8 s and 133.6 s in two of some 200 logged starts). The GPU process keeps executing the page's commands meanwhile (timer-query results come back). **Animation-frame watchdog** (main.js): the loop asks for one animation frame at a time, and when it has not come after 750 ms (400 ms before the view is ready: most start-ups saw such a stall of 1-3 s, before the first frame or after it) while the page is visible and the main thread was free, frames run from a timer (about 30 a second) until the browser delivers animation frames again, so the start-up goes on to ready. Offline recording (`rec=`) is never driven after ready, and a hidden page is never driven. `perf.init.firstFrameStall` records a stall before the view was ready, `app.perf.rafStalls` the later ones (the newest 8; `stats().rafStalls` counts all): `since` (ms since navigation when the frame was asked for), `frame` (frames run by then: 0 = the very first), `ms` (how long the animation frames were held back; it grows while the stall lasts, so the 'still loading' line shows it live), `visibilityState`, `hasFocus` (when noticed), `rafSeen` (an animation frame came again), `pumped` (frames run from the timer), `pumpMs` (the longest of them in CPU ms: seconds would mean its GL calls waited for a GPU process that was stuck itself), `gpuMs` (the newest GPU timer result then; 0: none came back), `lagMs` (the most the watchdog's timer ran late: the main thread busy).
- Worker teardown waits for the GPU process (Chrome releases a worker's GPU context, which it has once it used an OffscreenCanvas or an ImageBitmap, with a synchronous call). `Worker.prototype.terminate()` called during the start-up is carried out once every start-up program is linked (`perf.init.workersHeld` counts them), so a module may terminate its workers when their job is done, as before.
- From post's init until the start-up compile ends, the renderer's current render target is `app.post.sceneRT`: programs are compiled for the HDR scene target the post chain renders into (colour space, no tone mapping), and a module's own `renderer.compile` warm-up builds the scene-pass programs. Passes that render elsewhere set their own target.
- `renderer.compile` traverses every object, visible or not, but neither it nor `touchPrograms` pays a program's first draw: with a warm shader cache that first draw costs the GPU process 100–200 ms and shows as `gpu-wait` 8–10 frames later. A module gives each of its programs one non-empty draw before `app.ready` (vegetation, catenary and furniture draw an instance scaled to 1e-5, 2 m in front of the eye, until ready: `BatchSet` / `CatBatches` / `VegetationPools.warmup()` / `endWarmup()`).
- `app.perf.init` (ms): `imports` (since navigation, when every module import resolved), one entry per init, `modulesTotal` (all inits), `prime` (all start-up chunk builds; `primeLate` and `primeFar` are step 4's), `gpuWait` (from the end of step 2 until the warm-ups were done), `compileStart` (since navigation, when the scene's programs were queued), `programsQueued` (how many then), `initsQueued` (init time that ran alongside the compile), `compile` (from the queueing until every program was linked), `compileWait` (the part of it after the last init and build), `programs`, `workersHeld`, `firstFrame` (from the end of the compile to the first frame callback, a timer-driven one after a stall), `frames` (to the view being ready), `firstReady` (since navigation) and `firstFrameStall` (only after a stall, above). The wait for the programs is capped at 20 s; `compileTimeout: 1` marks a start-up that went on with programs still linking (seen only on an overloaded machine): note it next to anything odd in such a run. `app.perf.startFrames` holds `[t, cpu ms, programs]` of the first 40 frames. The loading bar follows the inits, then the programs as they finish.
- `app.perf.lightLoop`: core's `loopSpotLights(THREE.ShaderChunk)` (`src/core/lightLoops.js`), called right after env's init, turns the spot loop of `lights_fragment_begin` into a real loop when `NUM_SPOT_LIGHT_SHADOWS == 0` and `NUM_SPOT_LIGHT_MAPS == 0` (the unrolled original stays as the `#else`), which compiles in about 60 % of the time; false when the chunk does not have the expected shape. URL `lightloop=0` for A/B.

## Materials: `app.materials` (`src/materials/materials.js`)
- `get(name, opts?)` returns a shared material. `opts` (for example `{vertexColors: true}`) returns a cached variant, shared by every module asking for the same options. Use vertex colours for per-building stone tint and baked AO.
- `register(name, material)` adds your own material to the library. `track(material)` is **required for every material you put in the scene**, so the lighting system can configure it (shadows/CSM/fog). `onTrack(fn)`, `all()`, `names()`, `meta[name]`, `ready` (resolves when the GPU-baked maps are final; `init` does not wait for the bake).
- Names (all must exist): `stone.ashlar`, `stone.smooth`, `stone.rough`, `stone.dirty`, `paving.street`, `paving.sidewalk`, `paving.band`, `paving.platform`, `rail.head`, `rail.side`, `rail.groove`, `metal.iron`, `metal.pole`, `metal.galvanized`, `metal.steel`, `metal.wire`, `metal.rust`, `glass.shop`, `glass.window`, `glass.lamp`, `fabric.awning`, `fabric.umbrella`, `fabric.flag`, `wood.shutter`, `wood.door`, `wood.bench`, `paint.frame`, `paint.frameDetail`, `wood.shutterDetail`, `plastic.chair`, `concrete`, `roof.tile`, `roof.membrane`, `plaster`, `bark`, `bark.smooth`, `leaf`, `rubber`, `asphalt`, `sign.panel`, `emissive.warm`. (`ironwork.ac` no longer exists: AC units use `ironwork.parts`.) `bark.smooth` is for trunks under about 25 cm and branches.
- `meta[name]` publishes metrics for other modules: tile sizes and uv conventions, `stone.ashlar` `{courseH, blockL, tints, tintWeights, albedo}` (mean linear albedo of the baked limestone, about `[0.6, 0.47, 0.27]`; stand-ins such as the far field match it), `paving.street.albedo` `[0.157, 0.168, 0.192]`, `paving.band.albedo` `[0.214, 0.213, 0.207]`, `stone.rough.relief`, and `rail.head` `zones` (measured from the bake): the running band albedo (0.451, 0.446, 0.436), roughness 0.57, metal 1; the shoulder (0.254, 0.226, 0.2), 0.64, 0.59; the bevel and gauge corner (0.204, 0.161, 0.118), 0.72, 0.41; off the band the head is oxidised. A module that derives colours from a library albedo reads them from here rather than hard-coding them; env's canyon model assumes paving of about (0.17, 0.175, 0.185), so tell env when that changes substantially.
- Baked maps: `paving` is 2048² (1.6 mm per texel over the same 3.2 m tile and layout); the `canvas` tile is 0.4 m at 1024² (the fabric materials' `meta` tile follows). The row layouts of stone and paving stay fixed (buildings' `stoneMetas` reads them). `tools/textures/preview.html` shows the maps (`&zoom=<k>` shows 1/k of the tile, `&panel=<0..3>` one map at full height).
- Facade stone UVs: u = metres along the wall, v = metres up from `floorRef` (or world height), so ashlar courses line up across a facade.
- If you patch a material with `onBeforeCompile`, **chain** any existing hook (`const prev = m.onBeforeCompile; m.onBeforeCompile = (s, r) => { prev && prev(s, r); ... }`) and set `customProgramCacheKey`.
- One material object must not be drawn by both a `BatchedMesh` (or `InstancedMesh`) and a plain `Mesh`: three re-evaluates its program at every switch (CPU time and garbage each frame). Ask for a separate variant for the batched use.
- `envMapIntensity`: three ignores a material's `envMapIntensity` when the environment comes from `scene.environment` (it substitutes `scene.environmentIntensity`). Library materials honour it through their surface patch; on your own materials set `material.envMap` explicitly or scale the indirect specular in your shader.
- Surface features and program keys: the runtime surface patch (`src/materials/surface.js`) builds programs keyed `'sf7'` + `'S'` + the family's feature letters + per-material letters (A lane attribute, T translucency, N night emissive, G thin glass). Families: `lite`, `full` (`LJPDRWK`: stone, paving, concrete, plaster, roof tiles) and `relief` (`LDRWH`, key `sf7SLDRWH`, rock-faced stone only, selected by the library field `fx: 'relief'`). Feature H is parallax-occlusion relief of the height a recipe stores in the albedo alpha (`heightA: [lo, hi]`, metres encoded over lo..hi), marched through the row layout with a self-shadow march towards the sun and faded out with distance (full within about 20 m, gone by 35 m); roughness then comes from the height. `stone.rough` uses it: `meta.relief = [0, 0.095]` (the bosses stand up to 9.5 cm in front of the polygon), so signs, plates and lamps mounted over it stand off about 0.1 m; the outline of the mesh itself stays as modelled.
  - Library fields read by the patch: `surf.stain.stretch` stretches stains vertically along v (run-off on walls); `surf.stain.matt: true` makes stains darken the albedo without lowering the roughness (fabric.awning and fabric.umbrella carry such a stain layer); `surf.spots.blot = {prob, radius, albedo, rough}` (feature P) adds spill blots per global cell, 2–10 cm (lognormal), albedo × `albedo` and, in 60 % of them, roughness × `rough` (paving.street 0.045, paving.sidewalk 0.06).
  - Weathering (W): ledge soiling dusts every surface whose world normal is tilted up by more than about 25° (smoothstep 0.4–0.85 on n.y), so 45° chamfers and sloped sills collect it too.
- Night emission scales with `app.materials.uniforms.emissiveGain`: scale a module's night emissives with it rather than asking env to change the night ramp.
- `paving.street` accepts a `laneAttr` option.

## Lighting and image
### env (`src/env/env.js`, `src/env/lights.js`, `src/env/sky.js`)
Sky, sun, environment map, shadows, fog/haze, wind, time of day, exposure and the few real lights.
- `env.setTimeOfDay(t)` with t in [0, 1]: 0 midday, 0.55 golden hour, 0.8 sunset, 1 dusk. `env.state = {t, sunDir, sunElevation, night, lamps}`. It sets `U.uNight` (smoothstep over t 0.70–0.82), `U.uSunDir`, `U.uSunColor` and `U.uWind*`, and emits `tod`. `state.lamps` is the street lamps' level: their photocells switch them on from t 0.64, fully by 0.72, then they follow the night. The lamp lights, the lantern wash, the far pools, the airlight and catenary's lantern globes all follow it.
- Weather (`env.weather`, URL `sky=`): `streaks`, `cumulus` or `haze`, picked from the seed by default. Each regime carries its own aerosol load and street dust haze (`haze` is visibly milky). The aerosol extinction is one uniform, `uMieExt` (rgb, per km at unit density, from the Angstrom exponent `mieAng`), shared by the sky, the LUT and the cloud passes. `env.skySatScale` scales post's sky saturation boost (1 for streaks and cumulus, 0.5 for haze).
- Exposure: `env.exposureBase` is the nominal exposure (a 0.18 albedo under the horizontal illuminance, partial adaptation at dusk) lifted by `EXPO_LIFT` (a photograph of a sunny street exposes for the shade): +0.4 EV under the high sun (to t 0.3, so sunlit granite near the cab stays at about 165–180 sRGB with its setts apart), +0.8 at t 0.45, +1.2 at golden hour (t 0.55), +1.0 at t 0.65 and 0 from t 0.78 (the `env.tables.EXPO_LIFT` table, smooth between its points). `env.exposureMax` is the ceiling for the metered exposure, the minimum of three caps: the low-sun lit-stone cap (from about t 0.35, sun-facing stone stays on the tone curve's shoulder), the horizon cap (holds the sky slot down the street at `HORIZON_LEVEL`) and the dusk ceiling (from t 0.62: at most 1.8× the nominal exposure up to t 0.82, 4.2× in the blue hour). `env.exposure = min(exposureBase, exposureMax)`. Lit windows of the buildings follow it at night (`GLASS_NIGHT`: an exposed level of 0.3 at most), so they read as warm lamps behind curtains and never burn out.
- Colour outputs for post: `env.illuminant` (sun + sky on a horizontal surface in the open) and `env.sunIlluminant` (the direct sun alone, `U.uSunColor`). `env.skyIrradianceH` is the sky irradiance luminance on a level surface; shaders may read it instead of sampling the environment map.
- Sky irradiance: `env.sky.irradiance` = `{horizontal, horizonMean, zenith, vertical, horizonSun, horizonAnti}` (Vector3s, linear RGB), made once and updated in place, so a reference to it stays valid. It comes from a table built once at start-up (`sky.buildIrradianceTable`: the irradiance pass rendered for 129 times of day into one target and read back in one synchronous read), which `sky.irradianceAt(t)` interpolates: a time-of-day change reads nothing back from the GPU. Only when the table could not be built does env fall back to an asynchronous fenced read.
- Lights (`env.lights`): a pool of real spot lights, one per lantern (12 on high, 8 on med, 4 on low), reassigned every frame to the nearest lamp standards at dusk, plus `farLamps` (24 distant standards for post's screen-space pools). The shared light loop skips dark lights (colour 0) and spot lights outside their cone or range, so permanent light slots cost nothing when off. The headlight is the tram's dipped beam, told apart in the light loop by its decay `2.0001`: other modules must not create spot lights with decay above 2.00005. The light-struct uniforms upload through env's own typed setters (`env.lights.typedSetters` counts them).
- A canyon-bounce hemisphere light adds warm fill from sunlit stone. Next to it, env's `canyonCrossBounce` DirectionalLight carries the light of the sunlit facade across the street to the opposite one: horizontal, aimed at the camera from the sunlit side, coloured by the sunlit facade's reflected irradiance, and black (skipped) when no facade is in the sun. It stands for a 10–20 m area source, so it is **diffuse only**: the shared light loop puts back whatever `RE_Direct` adds to the specular, clearcoat and sheen terms for `directionalLights[]`, for every lighting model including patched ones (a specular term showed as white smudges in shop glass). It is the only entry of `directionalLights[]`, because the sun is a `SunLight` (`sunLights[]`). A module must not add a DirectionalLight of its own expecting speculars, and a custom shader that loops over `directionalLights[]` outside `RE_Direct` must take only the diffuse term.
- The environment cube holds a model of the street canyon (facades, floor, sky slot); it is the canyon occlusion for every glossy surface (rail steel, glass, paint). The trams compensate in their own shader for its bright, empty street level.

### Shadows (env)
- The sun uses 4 cascades in one atlas row, fitted to the field of view; its shadow camera reaches 700 m. Beyond it the far field shades its own street as a canyon (see World module contracts). Cascades 0-1 redraw every frame, cascade 2 every 2nd frame and cascade 3 every 4th; all redraw on camera or sun moves.
- High quality uses 4096-texel tiles (a 16384 × 4096 atlas; URL `shadowmap=<texels>`, capped at `maxTextureSize / cascades`). env creates the atlas itself, with an R8 colour attachment and 24-bit depth (320 MB). The PCF kernel is capped at 24 texels, with 32 taps for wide kernels and the coarse cascades.
- Cascades 2-3 skip `mesh.userData.thinCaster` meshes and casters under 1.5 texels. A numeric `thinCaster` is the largest cascade texel (m) at which the caster still draws.
- Static casters in a ready chunk are merged in the background into depth-only proxies. Set `mesh.userData.dynamicCaster = true` to keep a mesh out of merging; changes are detected automatically anyway.
- Every caster without a `customDepthMaterial` draws its shadow with a per-kind copy of the renderer's depth material, so the shadow pass never re-evaluates a program (`env.depthKinds = {switches, reevals, copies}`: the kind switches the shared material would see, the re-evaluations actually left, now 0, and the copies). Modules that set their own `customDepthMaterial` are left alone.
- Instanced casters may set `mesh.userData.shadowRange = [minViewDepth, maxViewDepth, margin]` each frame so cascades they cannot reach skip them.

### post (`src/env/post.js`): `render(dt, app)`, `setSize(w, h)`
HDR scene (MSAA, sub-pixel jitter) → SSAO → clouds → prepass (aerial perspective, shimmer, dusk airlight and lantern wash, circle of confusion; broken pixels filled) → TAA → DOF → motion blur → bloom → metered exposure → lens, local highlight recovery, sharpening, white balance, tone curve, grain.
- Tone: a camera tone curve (toe `[0.22, 0.06, 0.5]`, soft shoulder) with AgX colour and a soft black point `uBlack` (0.043 by day, 0.018 from t 0.6–0.85). Below the toe a deep-shadow term `uDeep` steepens the curve again (amount 0.95 by day easing to 0.3 over t 0.7–0.95, centred at −1.8 stops, 0.5 stops wide), so the deepest shade falls towards black as in a camera JPEG: by day −1 stop ≈ 77 sRGB, −2 ≈ 43, −3 ≈ 17, −4 ≈ 5. A little extra contrast at midday (1.12, above the pivot only) eases off by t 0.5. The values live in post.js `TONE`.
- Colour: street saturation `uSatOut` 1.15 by day and 1.2 at dusk, eased to 0.9 in the highlights. Sky pixels (depth = far) keep nearly the scene's colour ratios (chroma 0.95, URL `skychroma`), skip split toning, have their own saturated-sky gamut knee and get a saturation boost that is a vec2: blue sky 1.8 by day to 1.3 by the blue hour, warm sky 1.1 to 1.05 (URL `skysat` scales both, `env.skySatScale` too). A sunset hue twist (0.4) turns saturated warm sky pixels over t 0.6–0.9.
- Exposure: the final pass applies `min(uExposure × corr, uExposureMax)`, where `corr` is the meter's correction (by day the exposure follows the incident light and the meter only nudges it; from the low sun on the camera meters the scene) and `uExposureMax` is `env.exposureMax`.
- Highlight recovery: `uHiComp = (knee, slope)` compresses luminance above the knee in log terms with a soft knee. Knee (stops over mid grey): +1.6 by day, +1.2 at golden hour, +1.0 at sunset. Slope: 1 (off) at midday, 0.5 by t 0.3, 0.34 at golden hour, 0.27 at sunset, opening to 0.6 at dusk (URL `hslope` overrides it). Local highlight recovery in the final pass (URL `lhr=0` turns it off) works from a 1/8-resolution, sky-excluded, blurred map of the surfaces' log luminance (`post.localRT`): it applies above 2.5 stops over mid grey at strength 1 and fades out over t 0.8–0.9. The gamut knee's ceiling is white by day (start 0.84) and eases to 0.8/0.94 (street) and 0.72/0.86 (saturated sky) over t 0.6–0.75.
- Lens veil (final pass): `uVeil` (0.006) × the frame's mean HDR colour, which the LUM pass stores in `.gba` (`.r` holds the metering log-average), plus `uVeilSun`: the sun's colour × 0.0012 × sun intensity × exp(−angle / 0.25 rad) while the camera stands in sunlight (env's canyon shadow plane).
- White balance (`uWB`), on a warm-cool and a green-magenta axis. By day it balances on `env.sunIlluminant` (a daylight preset: sunlit grey paving reads neutral, the shade keeps its blue), correcting under a third of the sun's cast; between t 0.3 and 0.6 it blends to `env.illuminant` and keeps most of the evening warmth; from sunset (t 0.78) there is no warm-cool correction at all (a daylight-balanced camera: the lamp pools stay amber, the twilight blue), with a little extra blue in the blue hour. The gains stay on the daylight locus: the green gain within [0.99, 1.03] × sqrt(gR·gB), a neutral surface under the illuminant at G / mean(R, B) in [0.97, 1.0], and once the lamps light the street the green gain stays within 12 % of the red one (amber pools, never olive). Lit interiors and shop windows keep the warmth they are given at night.
- Lantern wash (prepass, at dusk): `uWash` (0.08 × `env.state.lamps`) adds each real lamp light's sideways and upward glow (`uLampPos`/`uLampI`, outside the spot cone, about 16 m reach) in screen space, on surfaces within 140 m of the camera (depth-reconstructed normal, albedo estimated from the ambient-lit colour). Beyond the real lights, `uFarLamp`/`uFarI` (from `env.lights.farLamps`) add the distant lamp pools the same way.
- Lantern halos: catenary draws each lantern's aureole (`catenary.glow`). Post's GLOW pass runs only while `app.systems.catenary.glow` is falsy (`catglow=0`, or catenary disabled), so every lantern has exactly one halo.
- Bloom: a share of the blurred pyramid (0.018 by day to 0.04 at night); at night a coarse pyramid level adds a wide tail (`uTail`).
- Temporal AA: the scene pass is rendered with a sub-pixel Halton (2, 3) jitter in the projection matrix (16 samples, `taaj` px peak to peak, default 0.5) and resolved against a reprojected history (new-frame weight 0.1, variance clipping). The history resets on cuts, jumps over 4 m and zooms. Only the projection is jittered: `projectionMatrixInverse` and the shadow cascades fitted from it stay unjittered. Frame-varying dither in a material (alpha hash, stochastic fades) averages out over about 10 frames, while a pattern fixed in screen space stays visible. URL: `taa=0`, `taaj=<px>`, `sharp=<k>` (final luma sharpening, default 0.8).
- `post.history` = `{texture, viewProj, camPos, fov, valid}`: the last resolved frame (scene-linear HDR before exposure) with its unjittered view-projection, camera position and field of view; `valid` is false while there is none (TAA off, a cut). Read it during the update phase, before the frame renders. The oncoming trams' glazing, windscreen and clear coat reflect the street from it (falling back to `taaOn/taaRT/taaPing/prevVP/taaValid/prevCamPos/prevFov`, so those names stay stable too).
- Motion blur: camera blur from `cameraRig.prevViewProj`, `cut` and `shutterSec`, capped at `cameraRig.blurMaxPx` (default 32 px at 1080 lines). Moving objects also blur and reproject correctly in TAA, as boxes in 8 mover slots (`NUM_MOVERS`): the oncoming trams from `app.trams.units[]` (`id, s, d, length, halfWidth, active, root.visible`: two route-following boxes per unit within 200 m, at most 4 slots; a jump over 6 m resets a unit's history), and the riding cyclists from `app.crowd.movers` = `{n, items: [{x, y, z (box centre), dx, dy, dz (movement since the last frame), heading, halfLen, halfWidth, halfHeight}]}`. A module with other moving objects publishes them in the same shape.
- SSAO scales `app.materials.uniforms.aoScale` to 0.6 while it runs. DOF models a 1"-type sensor: f/8 by day, f/2.8 at dusk.
- `debug=1`: post counts broken scene pixels (non-finite or negative HDR values) every 30 frames and reports the count as `stats().badPixels`. The read-back stalls, so this is for debug runs only. Post fills such pixels, but any non-zero count is a shader bug to fix at its source (for example a normalize of zero or a negative light value).

## Ride and people
- **train** (`src/ride/train.js`): `app.train = {s, speed (m/s), accel, throttle (−1..1), auto, state ('run'|'brake'|'dwell'|'depart'), nextStop, curvature, cruise, bellAt, t, holding, coasting, pedLoad, corridorCount, tram}`. `s` is the cab front along the route; `t` is the simulation clock. `holding` is true until the world is ready and, in the interactive app, until the start click: the tram doesn't move meanwhile. ## Streaming (`src/world/streaming.js`)
- Chunks within VIEW_BEHIND (60 m) behind to VIEW_FAR ahead are kept; builds are time-sliced (about 7 ms per frame), nearest first; chunks crossing a level boundary are rebuilt at the finer level and swapped in when ready (no gaps). A far chunk is replaced by the full chunk at VIEW_AHEAD, and parts of the old chunk with no counterpart (the far field) hide at the new chunk's first reveal.
- `world.prime(s, dist, onProgress, lods = null, only = null)` builds every wanted chunk within `dist` synchronously (start-up); `lods` limits it to those levels, and `only` (a Set of module names) builds just those modules' parts and leaves the rest pending for a later prime, which builds them and finishes the chunks (see Start-up).
- `app.world.upcoming(sCam, lookAhead = 0, out?)` lists the chunks the streamer will build next, `[{index, lod, dist, future}]` nearest first, including those that will be wanted, or upgraded to lod 0, within `lookAhead` metres of travel. It never lists lod 2. Pass an array of your own as `out` when you call it every frame: it is refilled in place, reusing its entries, so the call makes no garbage. `readyAround(s, dist)` ignores lod 2 as well.
- `stats().rideBuild` gives per-module ride-time build p50/p95/max over the last 200 builds; startup builds are excluded.
- New chunks compile their programs in the background before they are shown, then their parts reveal under a per-frame upload budget (4 MB). A module that pre-uploads vertex data can set `geometry.userData.revealBytes` to the bytes a reveal still sends.

## Shared-batch pattern (ironwork, reusable)
`build()` returns an empty marker group, and the meshes live in one scene-level group. A chunk's content starts drawing when its marker group becomes visible (or when it replaces an upgraded chunk) and is released on dispose. Shadow stand-ins are culled per block with the light's cascade frustum. BatchedMeshes should create their colour texture up front, so the startup compile doesn't build programs for empty batches, and give each program its first draw before ready (see Start-up).

## Frame timing, garbage and budget
**Budget (1920×1080; quality first, 30 fps minimum, 60 fps nice-to-have).** Photorealism has priority: spend headroom on image quality (shadow resolution and softness, AO, AA, geometric detail, crowd density) as long as the whole frame stays ≤ ~28 ms GPU / ≤ 20 ms CPU on this machine (RTX 4060 Ti) and riding has no hitches > 60 ms. Measure budget rides with `shoot.py --fps 30`.
- Draw calls under ~1500 including shadow passes. Keep triangles reasonable (under ~10 M including shadows) and avoid aliasing at all costs.
- Per chunk per module: build under 3 ms (lod 0), under 1 ms (lod 1). Prefer instancing and merged geometry. LOD 1 (over 200 m) should be much lighter: no small details that would sub-pixel alias at that distance.
- Thin geometry (wires, railings) must not alias or shimmer. Use pixel-width-aware shading or fade for far wires, and alpha-to-coverage with coverage-preserving mips or textures for fine ironwork and foliage far away.
- Cold start: target ≤ 10 s to ready on a quiet machine (`perf.init`, see Start-up).

**Frame monitor (`src/core/frameMonitor.js`).**
- `stats().frames` gives `{n, p50, p95, p99, max, over50, over60}`, the frame intervals in ms since ready (or since `app.resetFrames()`). `stats().hitches` counts frames over 50 ms.
- `app.hitches()` returns one record per frame interval over 50 ms (the newest 120). Each record has the route position and speed, the interval, the frame's CPU time and the gap outside the frame callback, and the CPU time of each stage (every module's `update`, `world` streaming and `render`) next to its `usualStages` value. The usual value is the median of the last 128 smooth frames. The record also has the shadow-pass CPU time and the cascades redrawn, the longest single draw in the shadow passes (`shadowDraw` ms and `shadowDrawObj`, its object name or type), the programs created in the frame (`syncCompile` counts those created inside render), the chunks compiling, the bytes revealed, whether a shadow-proxy merge ran, draw calls, the heap drop (a garbage collection), the frame's GPU time, post's section timers under `prof=1` and the browser's long-animation-frame script attribution. `app.hitchReport()` prints all of this one line per hitch (with `shadowDraw=ms(name)` when it is 2 ms or more), and `shoot.py --hitches` uses it.
- `cause` is a best guess: `sync-compile`; `contention` (every module update ran several times over its usual time at once, so the main thread was starved by other processes and no code path is to blame); `gc` / `gc-in-<stage>` (a heap drop with an excess under 250 ms); `gpu-wait` (render alone took several times its usual CPU for the usual draw calls, or the shadow excess is mostly one draw of over 10 ms: the main thread waited on the GPU; on a shared machine, usually another process's GPU work, and in an uncapped run the loop's own frames queued ahead); `cpu:<stage>` (one stage explains the excess: look at that module); `task:<fn>` (a timer or promise callback between frames); `idle-wait` (GPU or compositor back-pressure). Whatever the cause, `spikes` lists the modules that ran over 4× their usual time plus 5 ms, and the report header counts them per module. A module that keeps showing up there has a work unit that is too long for one frame and should split it; a prefetch budget must be a fixed number of milliseconds, not one that grows with a slow frame's `realDt`.

**Garbage.** A major collection pauses the main thread for 20–50 ms, and the minor ones come more often the more a frame allocates, so per-frame code must not allocate:
- No closures, arrays or objects per call in hot loops; pass `out` vectors and reuse scratch objects. `Array.prototype.sort` copies its array on every call: sort short per-frame lists with a small insertion sort.
- Numbers are garbage too: a non-inlined call boxes its float arguments and a float return value (and a uint32 above 2^30, such as a hash). Keep tight loops inside one function, write `v.x = …` rather than calling `v.set(…)` with computed floats in the hottest paths, and read results out of typed arrays. `Math.hypot` with three or more arguments allocates; use `Math.sqrt(x*x + y*y + z*z)`.
- A transparent `DoubleSide` material without `forceSinglePass = true` is drawn in two passes, and three re-evaluates its program on each one. The same happens to a material shared between instanced or batched and plain meshes (see Materials). Each re-evaluation builds a parameter object and a cache-key string.
- Core replaces three's per-frame internals that made garbage (`src/core/rendererPatches.js`): the render lists sort with a stable merge sort on persistent arrays in the same painter order (`glsort=0` for A/B; a custom `setOpaqueSort` / `setTransparentSort` still uses `Array.prototype.sort`); every linked program's float, vec2–4 and mat3/mat4 uniforms (single and array) get typed setters that compare against a `Float64Array` cache and upload from a `Float32Array` (`gltyped=0`; `app.perf.typedUniforms` counts them; the uniform objects gain fields `tc`, `tf`, `orig`, and env's light-struct setters are left alone); and `gl.uniform1f…4f` go through the vector forms with one reused typed array (`glbox=0`). Main applies the typed setters when it resolves a program's uniforms (`touchPrograms`) and to programs that became ready in a frame.
- Use `shoot.py --heapprof` to find allocation sites; compare per frame.
